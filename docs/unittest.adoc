= Unit Test
:toc:

== Overview

The unittest framework provides:

. Facilities for asserting on state.
. Facility to mock dependant functions.

- To get a overview of the basics of the framework see the SimpleExample
directory.
- More sophisticated features are noted in the ComplexExample directory.
- Finally, after understanding the above, to see how to cope with some of the
oddities of dealing with low level embedded systems see the EmbeddedExample
directory.

[NOTE]
====
The example projects have a copy of the UnitTest.h and test.sh files. Do not
use these copies in you projects. The publish version of these files
is in the framework folder.
====

== Dependencies
* C99 compatible C compiler
* bash version 3.1 or higher

== Configuration
When setting up the UnitTest you will need to customize the UnitTest.sh script
to accommodate the host compiler and any C language extensions that the target
compiler introduces. Ultimately the application code will need to be compiled by
both compilers. It is also important to try to (the best that you can) reproduce
the targets environment on the host.  The closer the hosts C environment is to
the target the better the inference is between the two with regard to the
applicability of the unit tests. For example it would be best if both
environments used the same size for an `int`.

=== Project Layout
UnitTest does assume your projects are structured in a specific way, as follows:
....
project
|-- build.sh                    Script to run unit tests then the application
|-- app/                        Directory for the application code
|  |-- include/                 Directory for application includes
|  |   |-- main.h               Top level "global" include
|  |   |-- module/              Directory for modules within application
|  |       |-- module.h         Public header for module
|  |       |-- module_p.h       Private header for module
|  |-- source/                  Directory for application source files
|      |-- main.c               Top level "global" source file
|      |-- module/              Directory for modules within application
|          |-- module.c         Module source file
|-- test/                       Directory for the unit tests
    |-- include/                Directory for unit test includes
    |   |-- UnitTest.h          The unit test macros
    |-- source/                 Directory for unit test source files
    |   |-- test_foo.c          Unit test for 'foo.c'
    |   |-- module              Directory for module within unit tests
    |   |   |-- test_module.c   Unit test for the module source 'module.c'
    |-- test.sh                 Unit test runner script
....

Some notes:

. The directory layout is required by the unit test runner script so it can scan
the `app/source` and `test/source` directories and auto correlate the unit test
to the application source files.
. The name of the unit test must match the name of the application source file
preceded with `test_`. The path to the files must also be mirrored under
'app/source' and 'test/source'.
. Application source files that do not have unit tests will be noted by the test
runner script.

For example the `app/module/module.c` and `test/module/test_module.c` files
will compiled together and run as a test by the unit test runner script.

=== Host Compiler

The unit test run on the host using the hosts native compiler.  A typical build
will run unit tests first then (provided all of the tests pass) the target
compiler will compile the application to be loaded and run on the target. The
application source is therefore processed by (at least) two C compilers.

.File usage by compiler
....
    project                   Target    Host (test)
    |-- app
    |   |-- source
    |   |   |-- foo.c         yes       yes
    |   |   |-- main.c        yes       yes
    |   |-- include
    |       |-- foo.h         yes       yes
    |       |-- main.h        yes       yes
    |-test
        |-- test.sh
        |-- source
        |   |-- test_foo.c    no        yes
        |-- include
            |-- UnitTest.h    no        yes
....

[NOTE]
====
It should possible to run the unit tests on the _target_. This is future work
planned for the framework. It should be possible to run the same unit tests on
the host (quickly during development) and on the target to support CI systems.
See https://github.com/nandgate/UnitTest/issues/1#issue-473003640
====

=== Use

Given above structure you may run the unit tests via the `test.sh` script.
(e.g. $./test.sh) To run the test for a specific module (and it's sub-modules)
you may specify the path to the module to the script (e.g. $./test.sh module).

When the unit test framework runs it uses a file called 'assertions.txt' for
tracking the number assertions during the run. When the framework fist tries
to write the file it will report errors in opening the file. This is normal and
expected behavior of the framework.

As stated above, the framework operates by matching a single application source
file to an single unit test file. These two source files are compiled and the
executable is run. This process repeats for each application/unit test pair.
The unit test must satisfy all of the external dependencies of the application
source file. If you find it hard to provide these dependencies most likely the
application source is not encapsulated enough and its functionality should be
split in to smaller pieces.

Note that because the test framework will only compile one application source
file it cannot be used for "integration tests".  However, it is important to
have within the project a strategy in place to test the code as a whole to
verify the interactions between the units. It is very possible to to create
unit tests that are asymmetric in how module is mocked vs its actual
implementation.

== Life Cycle
Each test file must call `Assert_Init()` at the start of `main()` and `Assert_Save()` at the end.
These accumulate the assertion count across all test binaries in a run via `assertions.txt`.

=== Mock_Vars(depth)
Declares the shared global state required by the framework. Must appear once per test file at
file scope, before any mock declarations. `depth` is the maximum number of calls tracked per mock.

    Mock_Vars(5);

Start with a depth of `5` — this is sufficient for most tests. If the depth is
exceeded at runtime the framework reports the mock name and depth that was
exceeded, then the test binary exits with a failure. When this happens, increase
`depth` until the failure clears.

=== Test_Init()
Resets shared test metadata (call order tracking, notes). Call once in `setUp()`.

    static void setUp(void) {
        Test_Init();
        Mock_Reset(Foo);
    }

=== Assert_Init()
Reads the running assertion count from `assertions.txt`. Call at the start of `main()`.

    int main(int argc, char **argv) {
        Assert_Init();
        test_Example();
        Assert_Save();
        return 0;
    }

=== Assert_Save()
Writes the running assertion count back to `assertions.txt`. Call at the end of `main()`.

== Assertion Failure Behavior

When an assertion fails, the framework prints the file name, line number, and a
description of the failure to stdout, then exits with the return code '1'. The test binary
terminates immediately — no subsequent assertions or test functions in that
binary will run.

This means:

* A test binary reports at most one failure per run.
* `Assert_Save()` is *not* called on failure, so the assertion count in
  `assertions.txt` is not updated for that binary.
* The `test.sh` runner detects the non-zero exit code and reports the binary as
  failed.

This allows the natural use of the test framework for TDD.

To diagnose a failure, look for the printed file and line number in the output,
fix the defect or test, and re-run.

When all tests complete without assertion the framework exits with a return code of '0'. This return code is used by the test runner to manage the continued execution of additional tests.

== Mock Behaviors

=== Mock_Reset(fn)
Resets all tracking data for the mock (call count, argument history, return value).
Call once per mock in `setUp()`.

    Mock_Reset(Foo);

=== Mock_Returns(fn, retValue)
Specifies a fixed return value for a mock. The mock returns this value on every call.

    Mock_Returns(Foo, 42);

=== Mock_ReturnsSequence(fn, len, seq)
Specifies a sequence of return values. The mock returns each value in order. Once the
sequence is exhausted the last value is repeated. Calling `Mock_ReturnsSequence` again
resets the sequence index to the beginning.

    uint8_t seq[] = {1, 2, 3};
    Mock_ReturnsSequence(Foo, 3, seq);

=== Mock_Custom(fn, custom)
Specifies a custom implementation function for the mock. Arguments are still captured
by the framework before the custom function is called.

    uint8_t myFoo(uint8_t a) { return a + 1; }

    Mock_Custom(Foo, myFoo);

== Asserts

=== Assert_ArrayEquals(len, expected, actual)
Asserts that the elements of two arrays are equal.

    uint8_t expected[] = {1, 2, 3};
    uint8_t actual[]   = {1, 2, 3};
    Assert_ArrayEquals(3, expected, actual);

=== Assert_Equals(expected, actual)
Asserts that two integer values are equal.

    Assert_Equals(42, result);

=== Assert_NotEquals(expected, actual)
Asserts that two integer values are not equal.

    Assert_NotEquals(0, result);

=== Assert_EqualsLong(expected, actual)
Asserts that two 64-bit integer values are equal.

    Assert_EqualsLong(0x1122334455667788, result);

=== Assert_EqualsFloat(expected, actual, delta)
Asserts that two floating point values are equal within the specified tolerance.

    Assert_EqualsFloat(3.14, result, 0.001);

=== Assert_True(actual)
Asserts that the value is true (non-zero).

    Assert_True(result > 0);

=== Assert_False(actual)
Asserts that the value is false (zero).

    Assert_False(errorFlag);

=== Assert_Fail(msg)
Unconditionally fails the test with the specified message.

    if (sizeof(int) != 4)
        Assert_Fail("int must be 4 bytes on this platform");

=== Assert_IsNotNull(actual)
Asserts that the pointer is not NULL.

    Assert_IsNotNull(ptr);

=== Assert_IsNull(actual)
Asserts that the pointer is NULL.

    Assert_IsNull(ptr);

=== Assert_StrEquals(expected, actual)
Asserts that two strings have the same length and content.

    Assert_StrEquals("hello", result);

=== Assert_Note(msg)
Sets a note to be displayed when any subsequent assertion fails. Useful when multiple
tests share a common assertion function and you need to identify which test case failed.
`Test_Init()` clears the note at the start of each test via `setUp()`.

    Assert_Note("test_MyFeature: checking boundary condition");
    Assert_Equals(expected, result);

== Mock Declarations
Mock declarations go at file scope, after `Mock_Vars` and before any functions.
The number suffix matches the number of arguments. The argument types must match
the real function's signature exactly.

=== Mock_Void(fn)
=== Mock_Void1(fn, arg0_t)
=== Mock_Void2(fn, arg0_t, arg1_t)
=== Mock_Void3(fn, arg0_t, arg1_t, arg2_t)
=== Mock_Void4(fn, arg0_t, arg1_t, arg2_t, arg3_t)
=== Mock_Void5(fn, arg0_t, arg1_t, arg2_t, arg3_t, arg4_t)
Declares a mock for a void function.

[source,C]
.Foo.h
----
#pragma once
void Foo(uint8_t a, uint32_t b);
----

[source,C]
.test_Bar.c
----
#include "Bar.h"
#include "Foo.h"
#include "UnitTest.h"

Mock_Vars(5);

Mock_Void2(Foo, uint8_t, uint32_t);

static void setUp(void)
{
    Test_Init();
    Mock_Reset(Foo);
}

static void test_Bar(void)
{
    setUp();

    Bar();

    Assert_CalledOnce(Foo);
    Assert_Called2(Foo, 1, 2);
}

int main(int argc, char **argv)
{
    Assert_Init();
    test_Bar();
    Assert_Save();
    return 0;
}
----

=== Mock_Value(ret_t, fn)
=== Mock_Value1(ret_t, fn, arg0_t)
=== Mock_Value2(ret_t, fn, arg0_t, arg1_t)
=== Mock_Value3(ret_t, fn, arg0_t, arg1_t, arg2_t)
=== Mock_Value4(ret_t, fn, arg0_t, arg1_t, arg2_t, arg3_t)
=== Mock_Value5(ret_t, fn, arg0_t, arg1_t, arg2_t, arg3_t, arg4_t)
Declares a mock for a function that returns a value. The return type is the first parameter.

[source,C]
.Foo.h
----
#pragma once
uint16_t Foo(uint8_t a, uint32_t b);
----

[source,C]
.test_Bar.c
----
#include "Bar.h"
#include "Foo.h"
#include "UnitTest.h"

Mock_Vars(5);

Mock_Value2(uint16_t, Foo, uint8_t, uint32_t);

static void setUp(void)
{
    Test_Init();
    Mock_Reset(Foo);
}

static void test_Bar(void)
{
    setUp();
    Mock_Returns(Foo, 42);

    Bar();

    Assert_CalledOnce(Foo);
    Assert_Called2(Foo, 10, 20);
}

int main(int argc, char **argv)
{
    Assert_Init();
    test_Bar();
    Assert_Save();
    return 0;
}
----

== Mock Assertions
The number suffix on argument-checking assertions matches the number of arguments
of the mock function being asserted on.

=== Assert_Returned(fn, expected)
Asserts that the mock returned the specified value at least once.

    Assert_Returned(Foo, 42);

=== Assert_CallCount(count, fn)
Asserts that the mock was called exactly `count` times.

    Assert_CallCount(3, Foo);

=== Assert_CalledOnce(fn)
Asserts that the mock was called exactly once.

    Assert_CalledOnce(Foo);

=== Assert_NotCalled(fn)
Asserts that the mock was never called.

    Assert_NotCalled(Foo);

=== Assert_CallOrder(fn1st, fn2nd)
Asserts that `fn1st` was called before `fn2nd`.

    Assert_CallOrder(Init, Process);

=== Assert_Called1(fn, arg0)
=== Assert_Called2(fn, arg0, arg1)
=== Assert_Called3(fn, arg0, arg1, arg2)
=== Assert_Called4(fn, arg0, arg1, arg2, arg3)
=== Assert_Called5(fn, arg0, arg1, arg2, arg3, arg4)
Asserts that the mock was invoked at least once with the specified arguments.
You may assert on fewer arguments than the mock declares — useful when you don't
care about the value of some arguments (e.g. pointers).

    Assert_Called2(Foo, 1, 42);
    Assert_Called1(Foo, 1);     // check only first arg, ignore second

=== Assert_CalledFirst1(fn, arg0)
=== Assert_CalledFirst2(fn, arg0, arg1)
=== Assert_CalledFirst3(fn, arg0, arg1, arg2)
=== Assert_CalledFirst4(fn, arg0, arg1, arg2, arg3)
=== Assert_CalledFirst5(fn, arg0, arg1, arg2, arg3, arg4)
Asserts that the first invocation of the mock had the specified arguments.

    Assert_CalledFirst1(Foo, 1);

=== Assert_CalledLast1(fn, arg0)
=== Assert_CalledLast2(fn, arg0, arg1)
=== Assert_CalledLast3(fn, arg0, arg1, arg2)
=== Assert_CalledLast4(fn, arg0, arg1, arg2, arg3)
=== Assert_CalledLast5(fn, arg0, arg1, arg2, arg3, arg4)
Asserts that the last invocation of the mock had the specified arguments.

    Assert_CalledLast1(Foo, 3);

=== Assert_CalledN1(n, fn, arg0)
=== Assert_CalledN2(n, fn, arg0, arg1)
=== Assert_CalledN3(n, fn, arg0, arg1, arg2)
=== Assert_CalledN4(n, fn, arg0, arg1, arg2, arg3)
=== Assert_CalledN5(n, fn, arg0, arg1, arg2, arg3, arg4)
Asserts that the Nth invocation (1-based) of the mock had the specified arguments.

    Assert_CalledN1(2, Foo, 2);   // 2nd call had arg0 == 2

=== Assert_AllCallsEquals1(fn, arg0)
=== Assert_AllCallsEquals2(fn, arg1)
=== Assert_AllCallsEquals3(fn, arg2)
=== Assert_AllCallsEquals4(fn, arg3)
=== Assert_AllCallsEquals5(fn, arg4)
Asserts that every invocation of the mock had the last argument equal to the
specified value. The parameter name reflects which argument position is checked
(`arg0` for 1-arg mocks, `arg1` for 2-arg mocks, etc.).

    // Foo(uint8_t a, uint32_t b) — assert all calls had b == 42
    Assert_AllCallsEquals2(Foo, 42);

=== Assert_AllCallsLessThan1(fn, arg0)
=== Assert_AllCallsLessThan2(fn, arg1)
=== Assert_AllCallsLessThan3(fn, arg2)
=== Assert_AllCallsLessThan4(fn, arg3)
=== Assert_AllCallsLessThan5(fn, arg4)
Asserts that every invocation of the mock had the last argument less than the
specified value.

    Assert_AllCallsLessThan2(Foo, 100);

=== Assert_AllCallsGreaterThan1(fn, arg0)
=== Assert_AllCallsGreaterThan2(fn, arg1)
=== Assert_AllCallsGreaterThan3(fn, arg2)
=== Assert_AllCallsGreaterThan4(fn, arg3)
=== Assert_AllCallsGreaterThan5(fn, arg4)
Asserts that every invocation of the mock had the last argument greater than the
specified value.

    Assert_AllCallsGreaterThan2(Foo, 0);

== Application Notes

=== Test File Conventions

A test file follows a fixed structure. These conventions are not enforced by the
compiler but are required for the framework to behave correctly. These conventions
are followed in the example below.

*File scope* — declare `Mock_Vars` first, then all mock declarations, then '#define's, then helper functions and test functions. No mock declarations inside functions.

*`setUp()`* — every test file defines a `static void setUp(void)` function, even when
no setup is required by the tests. It is always called at the top of every test function
— never from `main()`. It must call `Test_Init()` first, then `Mock_Reset()` for every mock declared in the file. Resetting mocks that are not used in a particular test is harmless and keeps `setUp()` unconditional.

*Test functions* — each test function is `static void`, takes no arguments, and
calls `setUp()` as its first statement. Test functions are named `test_<subject>`.

*`main()`* — calls `Assert_Init()` first, then each test function in order, then
`Assert_Save()`, then `return 0`. No test logic belongs in `main()`.

*Private headers* — test files include the module's private header (`module_p.h`)
rather than its public header, so that internal functions and definitions are
visible to the test.

=== Choosing an Argument Assertion

When a mock is called more than once, several assertion variants are available.
Choose based on what the test is actually verifying:

[cols="1,2"]
|===
|Assertion |Use when

|`Assert_CalledN(fn, ...)`
|You only care that the mock was called with these args at least once, and call
order does not matter. This is the most common called assertion.

|`Assert_CalledFirstN(fn, ...)`
|The first call's arguments are significant — for example, an initialization
value passed on startup. Can also be useful when the mock is called multiple times, asserting each call is usually unnecessary. Asserting the first and last call is
sufficient.

|`Assert_CalledLastN(fn, ...)`
|The final call's arguments are significant — for example, a flush or commit
value at the end of a sequence. Can also be useful when the mock is called multiple times, asserting each call is usually unnecessary. Asserting the first and last call is
sufficient.

|`Assert_CalledNN(n, fn, ...)`
|A specific call by position matters — for example, verifying the second of
three writes had a particular address.
|===

When the mock is called exactly once, all four variants are equivalent.
`Assert_CalledOnce` combined with `Assert_Called1` (or whichever arg count
applies) is the clearest way to express that case.

== Examples

=== Complete Test File
This example tests a module `foo_Doit()` that calls a dependency `foo_Add()` three times
and returns the sum of the results. The test file shows the full structure of a test file
and demonstrates several common patterns.

[source,C]
.foo_p.h
----
#pragma once
#include <stdint.h>

#define FOO_A0  10
#define FOO_B0  20
#define FOO_A1  30
#define FOO_B1  40
#define FOO_A2  50
#define FOO_B2  60

uint32_t foo_Add(uint32_t a, uint32_t b);
uint32_t foo_Doit(void);
----

[source,C]
.foo.c
----
#include "foo_p.h"

uint32_t foo_Doit(void)
{
    uint32_t sum;
    sum  = foo_Add(FOO_A0, FOO_B0);
    sum += foo_Add(FOO_A1, FOO_B1);
    sum += foo_Add(FOO_A2, FOO_B2);
    return sum;
}
----

[source,C]
.test_foo.c
----
#include "foo_p.h"
#include "UnitTest.h"

Mock_Vars(5);

Mock_Value2(uint32_t, foo_Add, uint32_t, uint32_t);

// A local variable used to capture state in a custom mock.
static uint32_t test_lastSum;

static void setUp(void)
{
    Test_Init();
    Mock_Reset(foo_Add);
    test_lastSum = 0;
}

static uint32_t test_Add(uint32_t a, uint32_t b)
{
    test_lastSum = a + b;
    return test_lastSum;
}

// Verify the mock is called with the correct arguments.
static void test_Arguments(void)
{
    setUp();
    Mock_Returns(foo_Add, 10);

    foo_Doit();

    Assert_CallCount(3, foo_Add);
    Assert_CalledFirst2(foo_Add, FOO_A0, FOO_B0);
    Assert_Called2(foo_Add, FOO_A1, FOO_B1);
    Assert_CalledLast2(foo_Add, FOO_A2, FOO_B2);
    Assert_CalledN2(2, foo_Add, FOO_A1, FOO_B1);

    // Assert on fewer args than the mock declares — useful when you
    // don't care about all argument values.
    Assert_Called1(foo_Add, FOO_A2);
}

// Verify the return value is the sum of the three foo_Add calls.
static void test_ReturnValue(void)
{
    setUp();
    Mock_Returns(foo_Add, 7);

    uint32_t result = foo_Doit();

    Assert_Equals(21, result);  // 7 + 7 + 7
}

// Verify behavior when foo_Add returns a sequence of values.
static void test_Sequence(void)
{
    setUp();
    uint32_t seq[] = {1, 2, 3};
    Mock_ReturnsSequence(foo_Add, 3, seq);

    uint32_t result = foo_Doit();

    Assert_Equals(6, result);   // 1 + 2 + 3
}

// Verify behavior using a custom mock implementation.
static void test_CustomMock(void)
{
    setUp();
    Mock_Custom(foo_Add, test_Add);

    foo_Doit();

    // The custom mock captured the last call's sum.
    Assert_Equals(FOO_A2 + FOO_B2, test_lastSum);
}

int main(int argc, char **argv)
{
    Assert_Init();

    test_Arguments();
    test_ReturnValue();
    test_Sequence();
    test_CustomMock();

    Assert_Save();
    return 0;
}
